**1. Current State Analysis:**
- Map existing monolithic structure: workflows/, bin/lib/, templates/, references/
- Identify software-engineering-specific logic vs. universal orchestration patterns
- List tightly coupled components requiring decoupling

**2. Target Architecture:**
```
.claude/get-shit-done/
├── core/                    # Universal orchestration engine
│   ├── engine.cjs          # Phase orchestration (questioning → research → roadmap → execute → verify)
│   ├── state.cjs           # STATE.md, ROADMAP.md, checkpoint management
│   ├── scheduler.cjs       # Agent scheduling, Task() mechanism, lifecycle
│   └── loader.cjs          # Scenario package loading and registration

│   └── software-eng/       # Existing software engineering workflows
│       ├── manifest.json
│       ├── workflows/
│       ├── agents/
│       └── templates/
└── bin/
    ├── lib/                 # Shared utilities (unchanged)
    └── gsd-tools.cjs       # CLI (updated to load scenarios)
```

**3. Decoupling Strategy:**
- **Core engine responsibilities:** Phase orchestration, state persistence, agent lifecycle, workflow execution
- **Scenario package responsibilities:** Domain-specific workflows, agent role definitions, templates, command registration
- **Interface contract:** manifest.json defines entry points, core engine handles execution

**4. Migration Path:**
- Extract core modules first (CORE-01, CORE-02, CORE-03)
- Move software-eng workflows to scenarios/ (SCEN-04)
- Implement scenario loader (SCEN-03)
- Add hot-switching support (SCEN-05)

**5. Backward Compatibility:**
- Existing commands must work without changes
- STATE.md, ROADMAP.md formats remain unchanged
- Git integration behavior preserved
- User-facing command names stay the same

**6. Risks and Mitigations:**
- Risk: Breaking existing workflows during refactor
  - Mitigation: Test suite running existing GSD commands after each extraction step
- Risk: Over-abstracting too early
  - Mitigation: Extract only what's proven generic (orchestration, state, scheduling)
- Risk: Circular dependencies during extraction
  - Mitigation: Dependency graph in this document, extract in correct order

  <action>
Create MANIFEST-SPEC.md defining the manifest.json schema for scenario packages. Include:

**1. Schema Definition:**
```json
{
  "name": "string (scenario identifier, e.g., 'software-eng')",
  "version": "string (semver, e.g., '1.0.0')",
  "description": "string (human-readable scenario description)",
  "gsd_version": "string (minimum compatible GSD core version)",
  "commands": [
    {
      "name": "string (command name, e.g., 'new-project')",
      "namespace": "string (e.g., 'gsd')",
      "workflow": "string (relative path, e.g., 'workflows/new-project.md')"
    }
  ],
  "agents": [
    {
      "role": "string (e.g., 'gsd-planner')",
      "workflow": "string (relative path, e.g., 'workflows/plan-phase.md')",
      "model_profile_key": "string (e.g., 'gsd-planner')"
    }
  ],
  "templates": [
    {
      "name": "string (e.g., 'project')",
      "path": "string (relative path, e.g., 'templates/project.md')"
    }
  ],
  "references": [
    {
      "name": "string (e.g., 'questioning')",
      "path": "string (relative path, e.g., 'references/questioning.md')"
    }
  ]
}
```

**2. Field Descriptions:**
- `name`: Unique scenario identifier (lowercase, hyphens, no spaces)
- `version`: Semantic versioning for scenario compatibility tracking
- `description`: One-sentence description of scenario purpose
- `gsd_version`: Minimum GSD core engine version required (ensures compatibility)
- `commands`: Array of command definitions registered to .claude/commands/
- `agents`: Array of agent role definitions for model profile resolution
- `templates`: Array of template files for document generation
- `references`: Array of reference documents used by workflows

**3. Example for software-eng scenario:**
```json
{
  "name": "software-eng",
  "version": "1.0.0",
  "description": "GSD software engineering workflow (questioning → research → roadmap → execute → verify)",
  "gsd_version": ">=1.0.0",
  "commands": [
    {"name": "new-project", "namespace": "gsd", "workflow": "workflows/new-project.md"},
    {"name": "plan-phase", "namespace": "gsd", "workflow": "workflows/plan-phase.md"},
    {"name": "execute-phase", "namespace": "gsd", "workflow": "workflows/execute-phase.md"}
  ],
  "agents": [
    {"role": "gsd-planner", "workflow": "workflows/plan-phase.md", "model_profile_key": "gsd-planner"},
    {"role": "gsd-executor", "workflow": "workflows/execute-plan.md", "model_profile_key": "gsd-executor"}
  ],
  "templates": [
    {"name": "project", "path": "templates/project.md"},
    {"name": "plan", "path": "templates/plan.md"}
  ],
  "references": [
    {"name": "questioning", "path": "references/questioning.md"},
    {"name": "git-integration", "path": "references/git-integration.md"}
  ]
}
```

**4. Validation Rules:**
- `name` must be unique across installed scenarios
- `workflow` paths must exist relative to scenario package root
- `namespace` must be valid (alphanumeric, hyphens, colons)
- All referenced files must exist when scenario loads

**5. Loading Behavior:**
- Core engine reads manifest.json on scenario initialization
- Commands registered to .claude/commands/{namespace}/ dynamically
- Agent roles added to model profile resolution table
- Templates and references made available to workflow execution context

  <action>
Create SCENARIO-STRUCTURE.md defining the standard directory layout for scenario packages. Include:

**1. Standard Structure:**
```
scenarios/{scenario-name}/
├── manifest.json          # Scenario metadata and registration (REQUIRED)
├── workflows/             # Workflow orchestration files (REQUIRED)
│   ├── {command}.md      # One file per command
│   └── ...
├── agents/                # Agent-specific workflow files (OPTIONAL)
│   ├── {role}.md         # One file per agent role
│   └── ...
├── templates/             # Document generation templates (OPTIONAL)
│   ├── {template}.md     # One file per template
│   └── ...
├── references/            # Reference documents for workflows (OPTIONAL)
│   ├── {reference}.md    # Shared knowledge for scenario
│   └── ...
└── README.md              # Scenario documentation (OPTIONAL)
```

**2. File Naming Conventions:**
- Scenario directory: lowercase-with-hyphens (e.g., `software-eng`, `agent-creator`)
- Workflow files: match command name (e.g., `new-project.md` for `/gsd:new-project`)
- Agent files: match role name (e.g., `gsd-planner.md`)
- Template files: semantic names (e.g., `project.md`, `plan.md`, `summary.md`)
- Reference files: topic-based (e.g., `questioning.md`, `tdd.md`)

**3. Required Files:**
- `manifest.json`: Must exist and validate against MANIFEST-SPEC.md schema
- `workflows/`: Must contain at least one .md file referenced in manifest commands
- All files referenced in manifest.json must exist

**4. Optional Directories:**
- `agents/`: Only needed if scenario defines specialized agent workflows
- `templates/`: Only needed if scenario generates documents
- `references/`: Only needed if scenario has shared knowledge documents
- `README.md`: Human-readable scenario documentation

**5. Path Resolution:**
- All paths in manifest.json are relative to scenario root
- Core engine resolves absolute paths: `.claude/get-shit-done/scenarios/{name}/{relative-path}`
- Workflows can reference scenario files using relative paths

**6. Example: software-eng scenario structure:**
```
scenarios/software-eng/
├── manifest.json
├── workflows/
│   ├── new-project.md
│   ├── plan-phase.md
│   ├── execute-phase.md
│   ├── verify-phase.md
│   └── ... (30+ workflow files)
├── agents/
│   ├── gsd-planner.md
│   ├── gsd-executor.md
│   └── ... (15 agent files)
├── templates/
│   ├── project.md
│   ├── plan.md
│   ├── summary.md
│   └── ... (10 template files)
├── references/
│   ├── questioning.md
│   ├── git-integration.md
│   ├── tdd.md
│   └── ... (12 reference files)
└── README.md
```
